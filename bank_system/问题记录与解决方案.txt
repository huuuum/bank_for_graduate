========================================================
银行客户定期存款认购预测系统
开发问题记录与解决方案（供论文撰写参考）
========================================================

【说明】本文档按开发阶段整理项目过程中遇到的主要技术问题、
原因分析与解决办法，可作为论文"系统实现"与"实验分析"章节的素材。

--------------------------------------------------------
一、环境搭建阶段
--------------------------------------------------------

问题1：Python 包下载速度慢
  · 现象：PySpark 安装包约 450MB，下载耗时约 12 分钟（657KB/s）
  · 原因：默认使用 PyPI 官方源，国内网络访问慢
  · 解决：配置 pip 国内镜像（清华源 pypi.tuna.tsinghua.edu.cn）
  · 效果：下载速度提升至 4.3MB/s，约为原来的 6.5 倍

问题2：缺少 Java/JDK 运行环境
  · 现象：系统无 java 命令，PySpark 无法启动 JVM
  · 原因：Spark 与 PyFlink 均基于 JVM，运行依赖 JDK
  · 解决：从清华 Adoptium 镜像下载免安装 JDK 17（Temurin 17.0.20.1），
          解压至本地目录，并持久化 JAVA_HOME 环境变量
  · 说明：Spark 4.x 与 Flink 均支持 JDK 17

问题3：PyCharm 虚拟环境内 PySpark 版本过旧
  · 现象：import pyspark 报错
          TypeError: code() argument 13 must be str, not int
  · 原因：项目 .venv 内 PySpark 为 3.0.3（2020 年版），其内置 cloudpickle
          使用了旧式 API，与 Python 3.14 不兼容
  · 解决：切换 PyCharm 解释器至全局 Python 3.14 环境（PySpark 4.2.0）
  · 经验：Python 版本与第三方库版本需匹配；过旧库在新版 Python 上
          可能因底层 API 变更而崩溃

--------------------------------------------------------
二、数据读取与路径
--------------------------------------------------------

问题4：相对路径找不到数据文件
  · 现象：FileNotFoundException: data/train.csv does not exist
  · 原因：PyCharm 默认将工作目录设为脚本所在目录，相对路径
          data/train.csv 被拼接到错误位置（code/spark_offline/data/...）
  · 解决：使用 pathlib 定位项目根目录，再拼接数据路径
          BASE_DIR = Path(__file__).resolve().parents[2]
  · 经验：代码读取数据应基于项目根目录定位，避免依赖运行时工作目录

--------------------------------------------------------
三、数据探索阶段
--------------------------------------------------------

问题5：缺失值的两种形态（null vs unknown）
  · 现象：isNull() 检查显示"无缺失值"，但数据实际存在大量 'unknown'
  · 原因：缺失值有两种形态：
          ① 显性缺失：null / NaN / 空值
          ② 隐性缺失：用特殊字符串占位，如 unknown / ? / - / 999
  · 解决：数据探索需同时检查 null 与各类特殊占位符
  · 数据情况：job(274)、marital(320)、education(994)、
          default(4860)、housing(886)、loan(889) 存在 unknown，
          其中 default 列最多（约 21.6%）
  · 经验：数据探索不能只查 null，必须主动寻找每个类别列的奇怪取值

问题6：占位符检查对数值列报类型错误
  · 现象：df.filter(F.col('age') == 'unknown') 报错
          CAST_INVALID_INPUT: 'unknown' cannot be cast to BIGINT
  · 原因：Spark 对数值列与字符串比较时，会尝试将字符串 cast 为数值
          类型，'unknown' 无法转换为数值导致异常
  · 解决：比较前先将列转换为字符串类型
          F.col(c).cast('string') == 'unknown'
  · 经验：跨类型比较前必须先统一类型

问题7：inferSchema 类型推断机制（概念澄清）
  · inferSchema=True 默认全量推断（samplingRatio 默认 1.0），并非抽样
  · 含 unknown 等非数字字符的列会被推断为 string 而非数值类型
  · 防御式做法：不依赖自动推断，显式检查各列的占位符与类型

--------------------------------------------------------
四、数据清洗阶段
--------------------------------------------------------

问题8：import 脚本导致重复输出
  · 现象：运行 step2 时，step1 的数据探索结果也被完整打印
  · 原因：from step1 import ... 会执行被导入模块的全部顶层代码
  · 解决：脚本之间不互相 import；公共逻辑抽取为函数，并用
          if __name__ == '__main__' 保护直接执行部分
  · 经验：带执行逻辑的脚本不应作为模块被 import

问题9：异常值判断需结合业务语义
  · 现象：将"负数"一律视为数据错误，误判了 emp_var_rate（就业变化率，
          9405 条为负）和 cons_conf_index（消费者信心指数，22500 条为负）
  · 原因：就业变化率、消费者信心指数等社会经济指标本身可为负
          （就业下降、信心悲观），负数是合法取值；数据为 2011-2013
          葡萄牙经济危机时期，消费者信心指数普遍为负
  · 解决：数据错误检查只针对"物理上必须非负"的列
          （age、duration、campaign、pdays、previous）
  · 经验：判断数据错误必须结合字段的物理/业务语义

问题10：approxQuantile 近似算法对极端分位数误差大
  · 现象：approxQuantile('age', [0.01], 0.01) 返回 16（=最小值），
          而非真实的 1% 分位数 21，导致 Winsorize 缩尾失效
  · 原因：approxQuantile 采用 Greenwald-Khanna 近似算法，
          relativeError=0.01 时极端分位数（1%、99%）的误差范围
          会覆盖到最小值/最大值
  · 解决：改用精确的 percentile 函数（Spark SQL）
          df.select(F.expr("percentile(col, array(0.01, 0.99))"))
  · 经验：approx 前缀代表近似算法；需要精确值时应选用精确函数

问题11：Windows 下 Spark 写文件需 winutils
  · 现象：df.write.csv 写本地文件报错
          第一层：HADOOP_HOME and hadoop.home.dir are unset
          第二层：下载 winutils 后报 UnsatisfiedLinkError
  · 原因：Spark 写文件时需调用 winutils.exe/hadoop.dll 设置文件权限；
          社区最新 winutils 仅到 hadoop-3.3.6，与 Spark 4.2.0 内置的
          Hadoop 3.5.0 版本不匹配，native 方法签名不一致
  · 解决：清洗结果改用 pandas to_csv 保存（纯 Python 写文件）；
          读数据、写 MySQL（JDBC）均不受 winutils 影响
  · 经验：Windows 环境下 Spark 读本地文件、写数据库不受 winutils 限制，
          仅"写本地文件"需要，可通过 pandas 等替代方案绕过

五、方法论总结（论文可引用）
--------------------------------------------------------

方法1：离群点检测方法选择
  · 3σ 原则：适用于近似正态分布的数据
  · IQR 法（Tukey 箱线图法）：对偏态/长尾分布稳健，本项目采用
  · 依据：duration 特征严重右偏（中位数 353 秒，99 分位 4833 秒），
          故选用 IQR 法（Q1-1.5×IQR ~ Q3+1.5×IQR 为正常范围）

方法2：离群点处理策略
  · 数据错误（物理不可能值）→ 修正或删除
  · 真实离群值 → Winsorize 缩尾（将超出 1%/99% 分位的值压到边界）
  · 缩尾 vs 截断：缩尾保留全部样本、仅压缩极端值，
          符合银行业"不轻易丢弃客户数据"的现实
  · 本项目缩尾结果：
          age      16~101   →  21~83
          duration 0~5149   →  14~4833
          campaign 0~57     →  0~45

方法3：类别不平衡处理（训练阶段待实现）
  · train.csv 标签分布：no 19548 条，yes 2952 条（约 6.6 : 1）
  · 计划采用 class_weight='balanced'，评估重点看 F1 与召回率
    （仅看准确率会因全预测 no 而虚高至约 87%）

方法4：缺失值填补策略
  · 类别列 'unknown' 采用众数填补（mode imputation）
  · 各列众数：job=admin.、marital=married、education=university.degree、
          default=no、housing=yes、loan=no

--------------------------------------------------------
六、关键决策与依据
--------------------------------------------------------

决策1：Spark 做特征工程、sklearn 训练模型
  · 原因：Flink 阶段（Python）需加载模型做实时推理，Spark ML 模型为
          JVM 私有格式无法加载，而 sklearn 模型可用 joblib 跨进程复用

决策2：特征处理规则导出 JSON 供 Flink 复用
  · 原因：保证离线训练与实时推理的特征处理逻辑"严格对齐"，
          避免因两套实现不一致导致预测效果错乱

决策3：流批一体架构
  · Spark 负责离线批量训练与统计；Flink 负责实时流预测；
          两者共用同一套数据集，离线训练的模型供实时任务加载

--------------------------------------------------------
七、Spark ML 组件使用要点（特征工程）
--------------------------------------------------------

要点1：Estimator 与 Transformer 范式
  · Estimator（估计器）：有 fit(df) 方法，从数据学习参数，
    返回 Transformer（模型）
  · Transformer（转换器）：有 transform(df) 方法，应用参数做转换
  · 例：StandardScaler.fit(df) 算出 mean/std → scaler_model.transform(df) 执行标准化
  · 意义：fit/transform 分离是"流批一体"的基础——离线 fit 学参数导出 JSON，
    实时 Flink 不 fit，直接读 JSON 做 transform

要点2：inputCol（单数）vs inputCols（复数）
  · VectorAssembler(inputCols=[...])：接受多个列，打包成一个向量
  · StandardScaler(inputCol="...")：只接受一个向量列
  · 因此数值特征需先 VectorAssembler 打包，再 StandardScaler 标准化

要点3：fit(df) 传数据表，inputCol 传列名
  · 构造组件时用 inputCol 指定"处理哪一列"
  · 调用 fit(df) 时传"整个数据表"，组件会从中找 inputCol 列计算参数

--------------------------------------------------------
八、特征工程阶段的代码问题
--------------------------------------------------------

问题12：生成器表达式 vs 列表
  · 现象：VectorAssembler(inputCols=num_cols) 报错
          Could not convert generator object to list of strings
  · 原因：(c for c in ...) 是生成器（惰性对象），(...) 是列表；
          Spark ML 组件的 inputCols 只接受列表
  · 解决：用方括号 [c for c in ...] 生成列表

问题13：筛选条件 or vs and
  · 现象：cat_cols 用 t == "string" or c != "subscribe" 导致几乎所有列都被保留
  · 原因：or 是"或"，只要满足一个条件就保留；排除某列需两个条件同时满足
  · 解决：用 and 叠加条件：t == "string" and c != "subscribe"

问题14：transform 结果赋错变量
  · 现象：scaled_df = scaler_model.transform(df) 后，后续仍用 df，
          导致 df 中无 scaled_num 列
  · 解决：统一用 df 覆盖赋值：df = scaler_model.transform(df)

问题15：模型对象 vs 模型数据
  · 现象：json.dump 报 Object of type StringIndexerModel is not JSON serializable
  · 原因：indexer_models[c] 是 StringIndexerModel 对象（Java 包装，不可序列化），
          .labels 才是可序列化的映射列表
  · 解决：导出 .labels（以及 scaler.mean/.std 用 .tolist() 转普通列表）
  · 经验：导出配置要存的是"数据"，不是"对象本身"

问题16：误导入无关模块
  · 现象：from idlelib import config 误导入 Python 自带 IDLE 模块
  · 原因：PyCharm 自动补全误引入
  · 解决：删除无关导入；注意检查 import 语句
